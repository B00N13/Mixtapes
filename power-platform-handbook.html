Logical container

Environment

Isolation for apps, flows, connections, identities/settings, capacity and (where provisioned) Dataverse. A tenant can have multiple environments.

Deployable container

Solution

Packages components for application lifecycle management; it isn't the same as an environment and does not package ordinary business records automatically.

Data platform

Dataverse

Tables, relationships, records, choices, business rules and role-based security. Model-driven apps sit naturally on top of it.

Behaviour

Apps and flows

A model-driven app presents forms/views; Power Automate runs event-based processes. Both work with Dataverse through the environment's permissions and connections.

Architecture in one sentence

The tenant governs identities and platform policies; environments host isolated application estates; solutions package deployable components; Dataverse stores data; apps and flows make the system useful.

The important separation

The DEV record ALM Test Project did not appear in UAT after the solution import. We created a separate UAT Deployment Test record there. Table definition is deployed with the solution; ordinary table data is not.

06 · Application lifecycle

Solutions, ALM & deployment

Manual release exercisedPipeline concepts documented

ALM = Application Lifecycle Management: managing design, development, testing, releases, support and eventual retirement. The same core architecture is used whether the deployment is manual or automated.

UnmanagedManaged
Editable source version, typically kept in DEV.Packaged release delivered to UAT/PROD.
Changes are made in the development solution.Direct changes to managed objects are restricted; managed properties and layering matter.
Useful for maker work and source exports.Useful for controlled import, upgrade and removal.

Our manual release procedure

1
Build in DEV

Make changes within the unmanaged BoonDigital Project Register solution. Test the app and flow.

2
Add deployable settings

Include connection reference and environment variable definition. Our text variable is boondv_EnvironmentName; current DEV value = DEV.

3
Control environment-specific values

The variable's Advanced setting showed Export value = No, so the current DEV value wasn't included in the managed package. Leave the default blank so target imports prompt for a value.

4
Publish & export

Use Publish all customizations → Export → Managed. We selected version 1.0.0.1 and generated BoonDigitalProjectRegister_1_0_0_1_managed.zip.

5
Import into target

Choose UAT in Power Apps → Solutions → Import solution. Browse the managed ZIP; enable included steps/flows when suitable; map authenticated connections and set Environment Name = UAT.

6
Verify after deployment

Review managed status, table, app, flow, connection references and variable values; validate a new UAT record. Check any import warnings separately.

Managed dependencies

The export wizard listed Microsoft-managed dependencies such as App Framework Infra Extensions and App Module Assets. A ZIP can export cleanly and still fail to import if target prerequisites, identities, capacity or privileges aren't satisfied.

Manual vs native Power Platform Pipelines

Manual deploymentNative Pipelines
Export and save a ZIP yourself.Platform automatically packages, stores and deploys the solution.
Choose Import solution in target environment.Deploy via a configured DEV → UAT → PROD stage.
Map connections/variables during import.Configure target deployment settings; reusable settings are possible.
Requires your own release record.Stores run history and artifacts for releases.
Appropriate for learning/one-off tasks.Useful for repeatable controlled deployments.

Does a native pipeline cost money?

There is no standalone per-click deployment fee; however pipeline targets require Managed Environments and appropriate premium-use rights. Host/target prerequisites, Dataverse capacity and licensing must be planned. Our UAT was Managed = No, so it wasn't ready as a pipeline target. Microsoft pipeline requirements.

Rollbacks, repairs and disaster recovery

MethodHow it worksRisk / caveat
Fix forward (often preferred)Revert the bug in DEV, publish and deploy a new higher version (e.g. 1.0.0.4).Must test the correction; preserves controlled version progression.
Manual older ZIPNot a simple direct downgrade; typically import a properly versioned corrected package.Managed solution downgrade is not the standard safe rollback path.
Pipeline previous releaseFrom run history, redeploy an older successful artifact if the setting permits.Destructive data/schema effects possible; Microsoft's warning must be taken seriously.
Environment backup restoreRestore whole environment state to a supported recovery point.Potential loss of legitimate records and unrelated changes since that point.
Temporary mitigationDisable affected flow, revert configuration or use feature flags when supported.Requires design and an operational playbook in advance.

Example: v1.0.0.3 breaks approvals, while v1.0.0.2 worked. A safe fix-forward might release repaired behaviour as v1.0.0.4. Prior-artifact pipeline redeployment is a separate, explicitly reviewed recovery path, not an automatic undo button. Microsoft redeployment warning.

Azure DevOps vs Jira vs native Pipelines

Jira manages work items and project tracking; Azure DevOps Boards can do similar planning, while Repos and Pipelines cover source control and deployment automation; native Power Platform Pipelines focus specifically on deploying Power Platform solutions. Jira can coexist with Azure DevOps Pipelines. Choose what solves the actual delivery problem, not solely based on vendor alignment.

08 · Security exercise

DLP and data policies

Policy design & wizard exercisedVerify saved state

Data Loss Prevention (DLP) policies in the classic Power Platform model govern which connectors are allowed and which connector groups can coexist in an app or flow. This is not a general-purpose sensitivity labelling or content-inspection system.

Business

Internal business services

Can be combined with other connectors in Business, not with Non-business connectors in the same app/flow.

Non-business

Separate permitted services

May be used independently, but not combined with Business connectors in the same resource.

Blocked

Prohibited connectors

Cannot be used where the policy applies; some built-in/core connectors cannot be blocked by classic policies.

What we configured in the wizard

ClassificationConnectors and count
Business (4)SharePoint; OneDrive for Business; Microsoft Dataverse (green connector); Office 365 Outlook
Non-business (1,770)Other connectors left in default grouping
Blocked (1)Dropbox
ScopeBoonDigital UAT only via Add multiple environments / Add to policy
Custom connectorsInspected fallback wildcard *; initially Ignore, then recommended changing to Non-business

Verify the final saved settings

We saw the Review and create policy screen and inspected the wildcard rule. The final saved policy and wildcard update weren't independently confirmed in the screenshots. Reopen BoonDigital UAT - Data Protection in Admin Center and verify it exists, its scope remains UAT only, and the * group is the intended value.

Why custom connector wildcard matters

The default wildcard * → Ignore may leave custom connectors unclassified by that policy and, when no other restrictions apply, allow them to combine with both Business and Non-business connectors. A conservative * → Non-business means new custom connectors aren't automatically allowed to connect to your Business group.

Classic versus advanced connector policies

Classic policies use Business / Non-business / Blocked groups. Microsoft also documents Advanced Connector Policies (ACP) with an explicit allowlist, per-environment/group control and more granular action-level restrictions for certified connectors. ACP doesn't fully replace classic rules for every connector category, especially custom/HTTP connectors. Check which governance model Westport actually uses.

Production caution

Apply a policy to the wrong environment and you can interrupt existing apps or flows. Policies can overlap, and the effective result can be more restrictive. Always document scope, conduct an impact assessment, communicate with owners and test before broad rollout.

People versus identities

Personal connections

Common and fast to build, but can create risk if the employee leaves, the account is disabled or credentials expire.

10 · Prepared technical lesson

Power BI — practical reference

Reference preparedNo report built yet

Power BI is the analytics and reporting layer used to connect to data, transform it, model relationships and measures, visualise results and distribute governed reports. The key distinction is between a report (visual presentation) and the semantic model that answers analytical queries.

SourcesDataverse · SQL · SharePoint · Excel · Fabric
→
Power QueryClean, join and reshape
→
Semantic modelTables · relationships · measures
→
Reports & dashboardsPublish · share · monitor

Terminology that matters

TermWhat it means
Power BI DesktopWindows authoring app: connect, transform, model, build reports.
Power BI ServiceOnline workspaces, publishing, semantic model refresh, access and sharing.
WorkspaceCollaboration/governance boundary for reports, models and related items; roles typically Admin, Member, Contributor, Viewer.
Semantic modelQueryable data model with tables, relationships, DAX measures and permissions. Older term: dataset.
ReportOne or more pages of visuals, often with filters and drill-through, usually built on a semantic model.
DashboardService-level canvas of pinned tiles; not the same as a multi-page report.
Power Query (M)Data acquisition and transformation; primarily before modelling.
DAXExpression language for measures and analytical calculations in the model.
GatewaySecure bridge for supported on-premises data sources and scheduled refresh.
RLSRow-level security: restricts which model rows each viewer can see.

Storage and refresh modes

ModeHow it worksTypical trade-off
ImportLoad source data into the semantic model; refresh to reflect changes.Often fastest visuals; refresh schedule and copy of data required.
DirectQueryQueries the source as users interact with reports.Fresher source access, but dependent on source latency, capabilities and query load.
Direct Lake (Fabric)Queries supported OneLake Delta data efficiently without conventional import.Requires compatible Fabric architecture and capacity; design restrictions apply.

Data modelling: think star schema

DimDateCalendar attributes
DimProjectProject, manager, status
FactSpendDate · ProjectKey · Amount

Use a fact table for events/transactions (such as monthly spend) and dimension tables for descriptive slicing (project, date, department). Prefer clear one-to-many relationships. Avoid ambiguous bi-directional filters or accidental many-to-many models without a reason.

DAX measures — illustrative examples

Total Budget = SUM(Projects[Budget])

Project Count = DISTINCTCOUNT(Projects[Project ID])

Total Spend = SUM(FactSpend[Amount])

Budget Variance = [Total Budget] - [Total Spend]

% Budget Used = DIVIDE([Total Spend], [Total Budget])

Illustrative DAX only: table/column names would need to match an actual model. Measures recalculate in filter context; calculated columns are evaluated/stored at data refresh.

Governance checklist for a Power BI estate

  • Which reports are business critical, and who owns them?
  • Are there shared, certified/endorsed semantic models or duplicated datasets?
  • Where does the source data live, who owns the gateway and credentials, and does refresh succeed?
  • How are Workspace roles, report permissions, RLS and external sharing controlled?
  • Are there DEV/TEST/PROD deployment pipelines or another release method?
  • What licences and capacity are used (Pro, PPU, Fabric capacity); what does monitoring show?

Microsoft Fabric — architecture reference

Reference preparedNo Fabric assets built yet

Microsoft Fabric is a broader, integrated SaaS analytics platform: ingesting, transforming, storing, engineering, analysing and reporting on data. Power BI is part of that ecosystem, not the entire platform.

Data sourcesBusiness apps · SQL · files · APIs · streams
→
Data Factory / DataflowsCopy · orchestrate · transform
→
OneLakeLakehouse / Warehouse / Eventhouse
→
Power BISemantic models & reports

Six building blocks

OneLake

The logical, tenant-wide data lake that underpins Fabric's data storage and discovery. Think of it as the shared foundation for multiple analytics experiences.

Lakehouse

Handles files and Delta tables together. Useful for raw data, engineering, notebooks and flexible structured/unstructured ingestion.

Warehouse

SQL-oriented relational analytics with warehouse-style modelling, tables and query access. Useful for curated business reporting.

Data Factory

Data pipelines and Dataflows Gen2 to ingest, schedule and transform data across systems.

Data Engineering / Science

Spark notebooks and engineering or analytical computation on stored data; useful when SQL alone isn't enough.

Real-Time Intelligence

Event ingestion, event processing and real-time query scenarios; choose for telemetry and streaming use cases.

Lakehouse vs warehouse: simple selection rule

QuestionLakehouseWarehouse
Primary development styleFiles/Delta, notebooks/Spark, SQL analytics endpointSQL-first relational analytics
Data shapeMixed raw and curated structured/unstructured dataCurated relational tables
Likely teamData engineering/scienceBI/data warehouse analysts and SQL engineers
Potential Power BI useSemantic model on Lakehouse dataSemantic model over warehouse tables

Medallion architecture

BronzeRaw landed data, preserve source history
→
SilverClean, standardise, validate, conform
→
GoldBusiness-ready curated analytics

For a Westport-style example, project data could arrive from multiple source applications, financial records and document libraries. Engineering pipelines might standardise project IDs and dates, apply business rules, then create curated gold tables for a Power BI portfolio dashboard. That's an illustrative pattern, not a claim about Westport's actual architecture.

What to ask if Westport uses Fabric

  • Is Fabric actually enabled, and what capacities/workspaces are licensed?
  • Do they use Lakehouses, Warehouses, OneLake shortcuts, pipelines or Dataflows Gen2?
  • Where are sources and transformations documented; which systems are authoritative?
  • Who owns permissions, privacy, lineage, refresh schedules and monitoring?
  • Are semantic models reusable and governed, or is every report duplicating its own transformation logic?

Practical learning path (for later)

  1. Create a personal Fabric workspace/capacity trial only when eligible and comfortable with expiry/costs.
  2. Load a synthetic project CSV into a Lakehouse and inspect files/tables/SQL endpoint.
  3. Use a Dataflow or pipeline to clean and load the data.
  4. Build a simple semantic model and Power BI report over the curated table.
  5. Inspect lineage, permissions, refresh/run history and costs.

Fabric is not required for every Power BI solution

A straightforward report can often connect to Dataverse or SQL directly without a Fabric Lakehouse or Warehouse. Architecture should follow data volume, integration needs, ownership, governance and cost—not just availability of new services.

Change controlTesting, approval, release notes, recovery plansInformal changes with unclear rollback
Portfolio visibilityBusiness criticality and roadmap documentedNo consistent view of demand, risk or ownership

Two possible environments you'll encounter

Scenario A · Established

Documented standards, solution control, security and release management are already in place. Learn the existing system, improve incrementally and avoid redundant tooling.

Scenario B · Still evolving

Inconsistent environments, scattered ownership, manual deployments and patchy documentation. Opportunity to help Jess create reliable visibility and standards—provided the organisation supports the effort.

Don't equate Jira with poor architecture

Jira may remain the right work-tracking tool even if deployment uses Azure DevOps or native Power Platform Pipelines. Distinguish planning maturity, technical architecture maturity and operational governance maturity.

15 · Onboarding plan

First days and first month

Suggested approach

Day 1–3: listen and map

  • Meet Jess, learn responsibilities, escalation paths and current pressure points.
  • Understand application estate size, critical services, immediate incidents and available documentation.
  • Discover who controls production access, how releases happen and where work is tracked.
  • Observe before proposing replacing Jira, changing environments or centralising credentials.

Week 1: form a working picture

  • Identify highest-criticality apps and flows and whether backup ownership exists.
  • Document a basic map: source → connector → flow/app → data → user/business outcome.
  • Check environment separation, solution status, premium licences and basic DLP scope.
  • Ask who sees flow failures and how production fixes are tested and released.

Weeks 2–4: agree priorities with Jess

  • Create or improve a lightweight inventory with agreed fields and ownership.
  • Pick low-risk quick wins: missing co-owner, runbook, failed-flow alert or release checklist.
  • Prioritise risks by business impact, ease of failure and likelihood—not aesthetics.
  • Identify where better ALM, monitoring or environment policy would measurably reduce rework.
  • Agree a simple improvement roadmap before introducing new tooling or controls.

Approach Jess as a collaborator: “What would make your life easier first?”

The goal is to reduce operational risk and workload, not judge existing decisions.

17 · Quick glossary

Terms at a glance

Tenant
Top-level Entra organisation and governance/licensing boundary.
Environment
Logical container for Power Platform apps, flows, settings and Dataverse.
Solution
Container for application components, used in ALM.
Publisher
Defines solution identity and schema prefix.
Unmanaged solution
Editable solution typically used in DEV.
Managed solution
Packaged deployable solution intended for controlled target releases.
Connection
Authenticated link between app/flow and a service.
Connection reference
Solution component that maps to a target connection.
Environment variable
Named configuration definition with different target-environment values.
DLP / Data policy
Connector governance rules and environment scope.
Dataverse
Power Platform data store with tables, relationships and security.
Business unit
Dataverse organisational security structure.
ALM
Application Lifecycle Management, from build to release and support.
Power Query
Data ingestion/transformation tooling using the M language.
DAX
Analytics calculation language used in Power BI semantic models.
Semantic model
Analytical tables, relationships, measures and security behind reports.
RLS
Row-level security; restricts which report/model rows users see.
OneLake
Fabric's shared logical data lake foundation.
Lakehouse
Flexible storage of files and Delta tables with analytics interfaces.
Warehouse
SQL-based curated relational analytics storage in Fabric.
Fix forward
Deploy a new higher-version release restoring correct behaviour.
Pipeline
Automates controlled movement of solution versions between environments.

How to update this GitHub-hosted handbook

  1. Keep the file as power-platform-handbook.html in the Mixtapes repository root beside your existing index.html. This avoids overwriting your current homepage.
  2. Upload a revised version using GitHub → Add file → Upload files → commit changes. Keep version history in Git.
  3. If GitHub Pages publishes from the main branch root, the expected path is /Mixtapes/power-platform-handbook.html.
  4. Bookmark the page on phone and desktop. Use the built-in search, contents and Print / Save PDF functions.
  5. When logging new work, use three clear labels: tested in lab, reference material, pending verification.

Why this guide omits live connection details

A GitHub Pages repository may be public even when it feels like a personal workspace.
